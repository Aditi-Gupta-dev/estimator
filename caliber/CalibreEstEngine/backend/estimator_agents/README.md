# Oracle Fusion Estimation Risk Agents (UC-1 / UC-2)

Implements **UC-1 (deviation % regressor)** and **UC-2 (overrun classifier)**,
trained directly on `Oracle_Fusion_Execution_Dataset_500_1.xlsx` (the 500
executed-project dataset one level up from this folder). Classical ML, no
GPU, no external API calls — runs on a single on-prem server/VM.

## What's here

```
estimator_agents/
├── src/
│   ├── features.py   # loads Project Master + Phase-Wise Effort, builds the 13-input feature matrix
│   ├── train.py      # trains + compares XGBoost / Random Forest / Ridge & Logistic, writes models/
│   ├── predict.py    # EstimationRiskEngine: scores a new estimate end-to-end
│   └── api.py        # FastAPI service exposing /score and /health
├── models/            # trained artifacts (regenerate with train.py)
│   ├── uc1_champion.joblib / uc2_champion.joblib      # winning model (xgboost or random_forest — see training_summary.json)
│   ├── uc1_ridge_explainable.joblib / uc2_logit_explainable.joblib
│   ├── uc1_quantile_p25.joblib / uc1_quantile_p75.joblib
│   ├── uc1_preprocessor.joblib / uc2_preprocessor.joblib
│   ├── explainable_twin_coefficients.json  # Ridge/Logit/quantile coefficients, portable to JS
│   ├── comparator_dataset.json             # 500-project feature set, for the "similar projects" lookup
│   └── training_summary.json               # model comparison, honest metrics
├── data/feature_matrix.csv  # regenerated by features.py — not committed
├── requirements.txt
└── README.md
```

## Running it

```bash
pip install -r requirements.txt
cd src
python features.py   # rebuilds data/feature_matrix.csv
python train.py      # retrains both use cases, regenerates everything in models/
python predict.py    # quick CLI smoke test
uvicorn api:app --host 0.0.0.0 --port 8000   # serves /score and /health
```

Example request:
```bash
curl -X POST http://localhost:8000/score -H "Content-Type: application/json" -d '{
  "complexity": "H", "industry": "BFSI", "n_modules": 4, "n_entities": 6,
  "integ_simple": 20, "integ_complex": 8, "n_reports": 25, "n_cemli": 12,
  "n_dm_objects": 15, "duration_months": 20, "team_size": 30,
  "integ_coverage_ratio": 0.67, "dm_coverage_ratio": 0.80
}'
```

The calibre-app frontend (`calibre-app/src/hooks/useEstimator.js`) computes
`integ_coverage_ratio` /
`dm_coverage_ratio` itself from its own 67-component bottom-up estimate vs
the template's per-unit baseline rate — see that file's comments for why
(the real actual/benchmark ratio only exists in hindsight, from real project
actuals, which isn't available at estimation time).

## What the models actually learned (honest numbers from this run)

`integ_coverage_ratio` / `dm_coverage_ratio` aren't raw dataset columns —
`features.py` derives them per-project from the `Phase-Wise Effort` sheet's
Actual/Benchmark ratio for "Ph4: Integration & SIT" and "Ph6: Data
Migration" respectively (clipped to [0.75, 2.25]). That's an approximation
of whatever the original feature-engineering pipeline did, so don't expect
bit-exact reproduction of any other run — regenerate via `train.py` if you
need fresh numbers instead of trusting numbers quoted here.

| Model | Metric | Value |
|---|---|---|
| UC-1 (champion: Random Forest) | Test RMSE | **14.85 pp** deviation |
| UC-1 | Test R² | 0.13 |
| UC-1 | 5-fold CV RMSE | 16.86 ± 1.07 pp |
| UC-2 (champion: XGBoost) | Test AUC | **0.711** |
| UC-2 | 5-fold CV AUC | 0.718 ± 0.06 |

**Read this honestly:** AUC ~0.71 means real but modest signal — enough to
flag risk, not enough to replace judgement. `integ_coverage_ratio` and
`complexity` are the strongest UC-2 drivers in this dataset (see a `/score`
response's `top_drivers`), consistent with coverage ratio being the
estimation-time proxy for "how much this estimate's own volumetric
assumptions diverge from typical projects."

**Why it's not higher:** 500 rows is a small training set, and the target
(`Overall Deviation %`) likely has genuine project-level noise (scope
changes mid-flight, client-side delays) no estimation-time feature set can
fully predict. The dataset's own `Overall Deviation %` distribution is also
skewed positive (76.6% of projects overran) — so even the "GREEN" risk band
still carries a ~65% empirical overrun rate; the bands separate *relative*
risk, not a low-risk band with a low absolute rate.

## Where this plugs in

`api.py`'s `/score` is called by `calibre-app`'s Node upload-server
(`upload-server/index.js` → `POST /api/score`, env-configurable via
`ESTIMATOR_URL`), which the React Oracle Fusion Estimator page calls. The
67-component bottom-up effort/cost/role-FTE math (Layer 1) runs entirely
client-side in the React app — this service only scores Layer 2 (deviation
%, overrun probability/band, comparators).
